## What is an Inference Engine


<figure>
<img src="/blog/assets/images/pasted-image-20260911162430345.png" alt="image" />
<figcaption>Inference Engine: end to end</figcaption>
</figure>


A definition I use for inference engines is that they are the orchestration layer of the complete LLM workflow. They handle the memory LLMs need, whether in permanent buffers, such as weights, or “temporary” ones, such as caches. They also handle the compute an LLM performs by orchestrating the execution of all its kernels. Finally, they make it possible to run this workflow for multiple requests concurrently, extracting more performance from these models.


## Why I built MTLQwen?

MTLQwen is an inference engine I built specifically for the Qwen 3.5 and 3.8 architectures, focusing on Metal backend for Apple GPUs. It started as a project to learn how inference engines work, but as I went deeper, I realized that specializing it for Qwen and Metal could provide more performance than general-purpose inference engines (vLLM or llama.cpp) on this specific model family and hardware. By using Metal specific features and optimizing Qwen’s kernels, MTLQwen ended up outperforming llama.cpp at both batch size 1 and in aggregate throughput, with a further 30% speedup when using DFlash.

### A Request Becomes a Sequence

The engine can receive requests from many kinds of frontends, whether they come from a multi-turn chat, an agentic TUI, or any other interface. The frontend is responsible for applying the model’s chat template and concatenating the conversation’s messages:

<figure>
<img src="/blog/assets/images/image.png" alt="image" />
<figcaption>Multiturn chat</figcaption>
</figure>

The resulting text is then [tokenized](https://platform.openai.com/tokenizer), producing the token IDs ready to enter into the inference engine. When the frontend submits a request, represented as an array of token IDs, the engine assigns it to one of eight available slots. These slots determine the maximum number of requests that can be active concurrently.

<figure>
<img src="/blog/assets/images/pasted-image-20260908200252881.png" alt="image" width="391" />
<figcaption>request assigned to a SLOT</figcaption>
</figure>

Each slot (also called Sequence in the code) contains the state the engine needs to process its assigned request. Its **`bindings table`** maps each part of the request’s KV cache to its location in physical memory, which we will explore in more detail later (Appendix A: Sparse Buffers). A **bank bit** tells the linear attention kernels which state buffer to read from and which one to write to, with the buffers alternating roles in a ping-pong pattern between forward passes. The **request** itself is an array of token IDs: it begins with the tokenized prompt and chat template, and each newly sampled token is appended to it. The **`kv_valid`** field records how many of those tokens already have valid KV state. During ordinary decoding, the most recently sampled token, also called the anchor token, has not yet passed through the model, so `kv_valid = len(request) - 1`. During speculative decoding, `kv_valid` also indicates how many proposed tokens were accepted by the target model and therefore have valid computed state. The **`busy`** flag indicates that some of the sequence’s tokens are currently participating in a forward pass, whereas **`active`** indicates that the sequence is live and still has work to perform.  



### Prefix Cache 

Most LLM applications combine the user’s message with a system prompt and tool definitions before sending a request to the model. Because this content forms a shared prefix across requests, the engine can compute its state once and reuse it.

The prefix cache stores checkpoints of this state for progressively longer token prefixes. Each checkpoint is identified by a chained hash, allowing the engine to find previously computed state without comparing entire token sequences.

<figure>
<img src="/blog/assets/images/pasted-image-20260909011019448.png" alt="image" />
<figcaption>Prefix cache</figcaption>
</figure>

The main design choice is the granularity at which prefixes are cached. Saving entries more frequently improves the hit rate but consumes more memory. Although Qwen 3.8’s linear-attention layers reduce the state required by each sequence, every prefix cache entry still needs about 50 MiB to store the GatedDeltaNet state for all 24 layers (see Appendix B). I currently use a 512-token interval as a reasonable tradeoff, though this value still needs to be tuned using real workload data.

With the prefix cache in place, we can return to what happens when a request enters a slot. The engine hashes the request’s 512 token prefixes and performs a cache lookup. On a hit, it copies the cached GDN state into the slot’s buffer selected by `bank`, preventing that cache entry from being modified by this new sequence. The corresponding physical KV-cache bindings are then installed in the slot’s `bindings table`.

<figure>
<img src="/blog/assets/images/pasted-image-20260909135650302.png" alt="image" />
<figcaption>Prefix Cache Hit</figcaption>
</figure>

### The Scheduler Forms a Batch

If we processed each sequence one at a time, we would not get any benefit from supporting concurrent requests. The aggregate speed, meaning the sum of all sequence speeds, would be at most the speed of a single request running in isolation. That is why we want to apply [Continuous Batching](https://huggingface.co/blog/continuous_batching). It allows us to send tokens from multiple sequences through the model together. The benefit comes from using the weights loaded from memory for more tokens, increasing the arithmetic intensity of the problem.

At this stage, every sequence has a `pending = len(request) - kv_valid` difference that depends on whether it had a prefix-cache hit. With some caveats (speculative decoding), this difference represents the number of tokens the sequence still needs to send through the model to compute their KV state.

The engine has a fixed capacity for each model pass, which is 128 tokens in MTLQwen. A scheduling policy decides how to divide this capacity between sequences. Sequences with `pending = 1` are in the t.g stage and, with speculative decoding enabled, send `n_draft` tokens through the target model. Sequences with `pending > 1` are in the p.p stage, where the scheduler can adjust the size of each processed chunk. Prioritizing p.p favors TTFT, while prioritizing t.g improves throughput and ITL.

<figure>
<img src="/blog/assets/images/pasted-image-20260909152811594.png" alt="image" />
<figcaption>Batch creation</figcaption>
</figure>

The scheduling policy I chose is simple: every live sequence advances on each step, which is possible because `max_slots * n_draft < 128`. Each t.g sequence (with spec decoding on) receives a `count` of `n_draft`, where `count` is the number of tokens it will compute. The remaining capacity is then divided equally between the p.p sequences. Each query also has a `state` property, which stores an offset into the candidates buffer. This buffer preserves the intermediate linear attention states produced while verifying proposed tokens (more on this later).

### Sparse K/V Memory Is Reserved

At this point, we know how many tokens each sequence will send through the model, so we can determine how much KV-cache memory it needs. My engine allocates this memory in 128-token blocks. If `kv_valid + count` crosses a 128-token boundary, the engine requests a new physical block from the OS heap and binds it to the sequence’s virtual address space (see Appendix A: Sparse Buffers).

<figure>
<img src="/blog/assets/images/pasted-image-20260909202722421.png" alt="image" />
<figcaption>KV Allocator</figcaption>
</figure>

This mapping is also recorded in the `bindings table`. The engine uses it when publishing a 512-token prefix to the prefix cache and when freeing physical blocks after a sequence ends. The kernels from this engine do not need to read this table, unlike engines such as vLLM. They access virtual memory directly, leaving the virtual-to-physical translation to the MMU.


### The Drafter Proposes Tokens

At this point, each sequence has the memory required for its next model pass. Its virtual-to-physical mappings are installed in the MMU and recorded in the sequence metadata, while `count` identifies how many request tokens it will compute. Each sequence also knows which GDN buffer to read from and write to. If it is using speculative decoding, it additionally knows where to store each verification token’s GDN state in the candidates buffer.

<figure>
<img src="/blog/assets/images/pasted-image-20260909204928165.png" alt="image" />
<figcaption>Packed DFLASH drafter batch</figcaption>
</figure>
<Sidenote>The tokens shown in the DFLASH model diagram are illustrative and do not correspond to the input batch.</Sidenote>

We first build a packed batch containing every Sequence that requires a drafter forward pass, identified by `state != unbound` (see the Batch building section). Each Sequence follows the drafter’s input format: its anchor token (the last sampled token whose KV has not yet been computed) followed by `n_draft` mask tokens. The drafter then proposes `n_draft` tokens for each Sequence. These proposals are later combined with the tokens from those queries with `state = unbound` (speculative decoding off or p.p stage) to form the target-model batch.

### Inputs Are Packed for the GPU

Now that we have the drafter proposals and the remaining target queries, we can pack the input batch and build the metadata the model needs to correctly process these tokens. As shown in this [Continuous Batching](https://huggingface.co/blog/continuous_batching) explanation, the attention kernels must prevent tokens from interacting across Sequence boundaries. For this, we build `queryStartLoc`, where `queryStartLoc[i]` gives the starting offset of Sequence `i` in the packed `inputIds`. The final entry marks where the packed input ends.

<figure>
<img src="/blog/assets/images/pasted-image-20260910020941127.png" alt="image" />
<figcaption>Batched Attention</figcaption>
</figure>

`sequenceSlots[i]` and `batchedKvValid[i]` locate each Sequence’s existing KV state. `sequenceSlots[i]` identifies its slot, while `batchedKvValid[i]` gives the offset where the new KV computation begins. Everything in `[0, kv_valid)` has already been computed and is used as attention context.

### The Target Model Runs

At this point, the packed `inputIds` and all the metadata needed to keep each Sequence isolated are ready, so we can run the target model. The kernels need to implement the Qwen 3.8 architecture shown below, as long as their results remain within a reasonable numerical tolerance of a reference Qwen implementation (could be in PyTorch or tinygrad) and they handle the intersequence masking described previously, each part of the architecture can be implemented however we want. This means I can choose how each operation is implemented and which operations are fused together. Since the model runs on a native Metal C++ backend I built, I can profile these kernels through native `.gputrace` and iterate them until reaching a very good performance level.
<Sidenote>Most of the performance gains in my engine came from optimizing the quantized linear kernels, which dominate runtime on each forward pass, alongside a decode optimized FlashAttention 2 kernel and a chunked parallel scan that computes the GatedDeltaNet state in 32-token blocks for p.p sequences. *More on these kernel optimizations in a future blog*.</Sidenote>

<img src="/blog/assets/images/pasted-image-20260911135514490.png" alt="image" />
<figcaption>Qwen 3.8 Architecture (Sebastian Raschka diagram)</figcaption>
</figure>

Once the packed batch has run through these kernels, we have the target samples needed to verify the drafter proposals, along with the KV cache and GDN state computed for every Sequence in the batch.

### State is injected to the drafter

As shown in the packed DFlash pass, the drafter relies on context produced by the target model. During each target pass, besides updating the target KV cache and sampling where required, we encode this context into the drafter’s cache.

<figure>
<img src="/blog/assets/images/pasted-image-20260910141754697.png" alt="image" width="508" />
<figcaption>Drafter context injection</figcaption>
</figure>

For every processed token $t$, we capture the target hidden states after layers 2, 6, 10, 14, 18, 22, 26, and 30. These are concatenated and projected down to the drafter’s hidden dimension, producing the context representation $H_{\text{ctx},t}$.

Each of DFlash’s six attention layers projects $H_{\text{ctx},t}$ into its own $K_{\text{ctx}},V_{\text{ctx}}$. These are stored in the same physical cache bundles as the target KV and addressed by `(sequence slot, token position)` (see Appendix A). During drafting, the cached context K/V is attended together with the temporary K/V produced by the packed anchor and mask tokens.

### Tokens and State Are Committed

For Sequences using speculative decoding, we first compare each drafter proposal with the corresponding target sample. My engine uses greedy decoding, so a proposal is accepted only when both tokens are equal. [Sampling-based verification](https://proceedings.mlr.press/v202/leviathan23a.html) instead draws `u ~ U(0,1)` and accepts with probability `min(1, p_k / q_k)`. This can accept proposals based on probability overlap rather than exact equality, but requires retaining `vocab_size` probability distributions for each proposed token until verification and resampling ends. <Sidenote>I still need to evaluate whether the higher acceptance rate is worth this memory cost.</Sidenote> We then commit the accepted prefix by advancing `kv_valid` by the number of accepted tokens. With greedy decoding, the target sample at the first mismatch becomes the new anchor and is appended to `request` for the next forward pass.
<figure>
<img src="/blog/assets/images/pasted-image-20260910150856258.png" alt="image" />
<figcaption>Compare &amp; Commit state</figcaption>
</figure>

This is where the purpose of the `candidateStates` buffer mentioned in the Batch Building section becomes clear. In linear-attention models, the memory is a fixed-size matrix updated in place as tokens pass through the model. If we wrote the final state directly into the slot and then rejected the last proposal, that state would still include an unaccepted token. In the figure, rejecting D would leave us with an invalid state. Instead, we save the state after each proposal in `candidateStates`, then copy only the state after the last accepted proposal into the slot’s GDN buffer selected by `bank`. If C is the last accepted proposal, we commit the state produced after C.

Tokens from p.p queries and t.g queries with speculative decoding disabled advance without verification. For a p.p Sequence, every token processed in this pass is already part of `request`, so `kv_valid` advances by `count`. For a non-speculative t.g Sequence, the previous anchor now has its KV computed, so `kv_valid` advances by one and the target sample is appended to `request` as the new anchor.

Every Sequence that crosses a 512-token boundary then extends its prefix hash with the newly completed 512-token chunk and publishes an entry to the prefix cache. This entry contains the GDN state after the final token in that prefix, together with all the KV-cache bindings needed to restore it in another slot.

At this point, one engine step is complete. The engine can accept new requests into available slots and send the remaining live Sequences back through the loop until the request ends.

## Design Tradeoffs and Current Limitations

- The current 512-token prefix granularity gets few hits because the prefixes are too long. Shorter intervals would improve the hit rate but make memory usage explode. One possible solution is to publish shorter prefixes only up to `request[max_prefix]`, where the data says reuse is more likely.

- The engine currently supports Qwen 3.8 and 3.5, which share the same architecture. Supporting more models should be straightforward, with new kernels required only when an architecture introduces different operations, such as Kimi’s linear attention or DeepSeek’s MLA. Sliding-window attention is probably the next addition, since more models are adopting it.

- I still need to tune the current 128-token block size. Smaller blocks waste less memory when partially filled but require more frequent allocations, while larger blocks reduce allocation overhead at the cost of more unused memory.


## Appendix A: Sparse Buffers

There is a very good [blog post](https://trymirai.com/blog/sparse-buffers-for-kv-cache) explaining how sparse buffers work and why they are useful for KV caches. In short, sparse buffers allow us to reserve a large contiguous virtual address range for every slot in our engine, enough to hold the KV cache for `maxContext = 65k` tokens without committing that amount of physical memory upfront (like `llama.cpp` does).

<figure>
<img src="/blog/assets/images/pasted-image-20260911142238675.png" alt="image" />
<figcaption>Cache Pool</figcaption>
</figure>

In my engine, the KV cache is managed in 128-token logical blocks. To simplify allocation and addressing, all cache tiles for one block across every layer and cache type (`Target K`, `Target V`, `DFlash K`, and `DFlash V`) are allocated as a single physical bundle. Each tile is a 256 KiB page holding 128 tokens for one `(cache, layer)` pair, so with DFlash enabled, a bundle contains 28 tiles and occupies 7 MiB. As with virtual memory in an operating system, these bundles do not need to follow the logical ordering in physical memory. Before each forward pass, we find which logical blocks the batch will touch and allocate any missing bundles from the shared placement heap pool (see the cache pool figure). Their tiles are then mapped into the corresponding sparse K/V buffers. Metal records these mappings in the GPU page tables, and the MMU handles the translation, keeping tokens contiguous within each virtual K/V layer region even when their physical backing is not.
<figure>
<img src="/blog/assets/images/pasted-image-20260911150221642.png" alt="image" />
<figcaption>Virtual to Phyisical Mappings</figcaption>
</figure>

All slots allocate from the same physical pool. When a Sequence is destroyed, its mappings are removed and any unreferenced bundles return to the pool. When reusing a cached prefix, the same physical bundles can also be mapped into the virtual blocks of multiple slots. In addition, each bundle has a `ref_cnt`, similar to vLLM, which tracks how many mappings reference it and whether it can be evicted when memory is limited.

## Appendix B: Standar Attention vs GDN State


<figure>
<img src="/blog/assets/images/pasted-image-20260911160405995.png" alt="image" />
<figcaption>Standard Attention vs GDN State</figcaption>
</figure>

In standard causal attention, the query for “table” attends to the K and V projections of every token up to and including itself. Its own projections are then appended to the KV cache for subsequent tokens. The cache grows linearly with sequence length.

GatedDeltaNet instead compresses the entire prefix "memory" into a fixed size recurrent matrix and a small convolution state (50 MiB for Qwen 3.5). Both are updated after every token, so the memory required to maintain one Sequence remains constant as its context grows. *This is the main advantage linear attention brings to the table.*

This compression makes sharing prefixes more complicated. With a KV cache, the K/V projections are stored per token, so if two requests share the first $n$ tokens, we can reuse the cache up to that point. A GDN state represents one exact prefix and cannot be rolled back to an earlier one. Supporting $P$ prefix boundaries therefore means either storing $P$ full GDN state snapshots, which removes its memory advantage, or recomputing from an earlier checkpoint, which removes much of the speedup from prefix caching. *One final difference is that KV-cache reuse can point multiple Sequences to the same physical blocks because those blocks remain read-only. GDN state is overwritten as a Sequence advances, so each cached state needs dedicated prefix-cache memory and must be copied into the slot when reused.*

The tradeoff I adopted for this engine is to cache prefixes at a much coarser granularity than other engines, using 512 token boundaries. This keeps prefix-cache memory usage manageable while still allowing hits on long shared prefixes, such as system prompts and tool definitions.
